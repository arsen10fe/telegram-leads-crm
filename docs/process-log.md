## Шаг 3. Второй проход по плану

**Когда:** 2026-10-02, ~02:00–02:20 MSK  
**Инструмент:** Claude Code, скилл `/aif-improve`

**Промпт (дословно):**

> /aif-improve

**Что сделал агент:** сверил допущения плана с документацией и реальными исходниками
библиотек, а не с памятью. Нашёл 13 проблем и 2 ошибки в зависимостях. Самые показательные:

- **Процесс бота упал бы при старте**, если бы общий модуль импортировал `server-only`. В исходнике
  пакета видно, что в обычном Node он бросает исключение. Решение: правило ESLint на границы
  модулей и тест, который загружает модули так же, как процесс бота.
- **Каждый деплой затирал бы базу знаний, отредактированную в CRM:** сид запускается при каждой
  выкатке. Сделали сид, который только создаёт записи.
- **За nginx все формы в проде вернули бы «Invalid Server Actions request»:** Next сверяет `Origin`
  с `x-forwarded-host`, это подтверждено документацией. Добавили заголовки и шаг проверки.
- **Менеджер не видел бы, что клиент написал снова:** список был отсортирован по дате создания.
  Ввели сортировку по последней активности и бейдж «Ждёт ответа».
- **Время в контейнерах шло бы в UTC.** Закрепили часовой пояс Europe/Moscow.
- **Сомнение с zod 4 снято:** в установленном `openai@6.37` объявлена совместимость с `^4.0`.
- **Самую большую задачу разделили:** API для AI переехал на второй день, первый день разгрузился.

**Решения:** приняли всё, кроме уведомлений менеджеру о каждом новом сообщении. Оставили, как
договаривались: только новый лид и передача от автопилота. Итог — 29 задач.

## Шаг 7. Независимое ревью безопасности и исправления

**Когда:** 2026-10-02, 03:25–03:40 MSK  
**Инструмент:** Claude Code, фоновый субагент `security-sidecar` (только чтение) + исправления

**Что сделал агент:** запустил отдельного агента-аудитора с узкой задачей: авторизация, все
Server Actions, экранирование в Telegram, защита промптов, секреты, XSS. Critical и high не
нашлось; 3 medium и 5 low. Исправили всё, кроме одного, с тестами на каждую атаку (248 тестов).

| Находка | Исправление |
|---|---|

## Шаг 9. План деплоя на общий сервер

**Когда:** 2026-10-02, 10:55–11:20 MSK  
**Инструмент:** Claude Code, `/aif-plan` (режим Full) + проверки сервера только на чтение по SSH

**Промпт (дословно, секреты скрыты):**
> да, давай сделаем деплой там, но аккуратно, чтобы все остальное работало и никаких проблем не было. токен бота [скрыт]

**Что сделал агент:** перед планированием снял с общего сервера (Timeweb, Амстердам; на нём ещё
около 20 сайтов) инвентаризацию только на чтение: порты, память, диск, контейнеры, сети Docker,
nginx и `nginx -t`, сертификаты, cron, DNS. Проверил токен бота и ключ OpenAI вызовами, которые
ничего не меняют (`getMe`, `getWebhookInfo`, список моделей). Взял правила работы с этим хостом из
инструкции по деплою прошлого проекта (meet_ai). Секреты положил в локальный `.env.server`: он не
попадает в git и Docker, а на сервер уходит через stdin ssh, не через аргументы команд. Итог —
план `.ai-factory/plans/deploy-shared-vps.md`, 11 задач.

**Решения и почему:**
- Адрес `lidogram.72-56-101-176.sslip.io`, чтобы не ждать DNS (выбор пользователя). AI на проде
  включён, модели `gpt-5.4-nano` / `gpt-5.4-mini`: проверено, что ключу они доступны. Профиль
  бота не меняем.
- Найдено до деплоя: у бота выключен Business Mode (`can_connect_to_business: false`). Без него
  требование 2 не подключить, это шаг пользователя в BotFather.
- Найдено до деплоя: сервер дважды перезагружался за две недели, а Docker поднимает контейнеры без
  порядка из compose. Бот мог стартовать раньше базы и потерять заявки, накопленные за простой.
  В план добавлено ожидание базы перед приёмом сообщений.
- Чтобы не задеть соседей:
  - сервис Caddy вынесен из `compose.prod.yml`, чтобы этот файл не мог занять порты 80/443;
  - порт 3700 только на `127.0.0.1`;
  - образ собирается один раз, с проверками памяти и диска до и во время сборки;
  - `nginx -t` читаем глазами (ровно 3 известных предупреждения), потом `reload`, никогда `restart`;
  - бэкап в отдельном `/etc/cron.d/lidogram`, общий crontab не трогаем;
  - снимок сервера до и после деплоя, разница допускается только в наших объектах.
- Снимки сервера не коммитим: в них чужие проекты и домены, а репозиторий уйдёт работодателю.

**Уточнение плана (`/aif-improve`, 11:20–11:50 MSK).** Во время анализа пользователь написал
(дословно): «очень важно ничего не сломатб на сервере прям супер важно». Это стало главным
критерием. Повторные проверки сервера — только на чтение. Пользователь принял все правки:
- В план добавлены обязательные «Правила безопасности сервера»:
  - список запретов: никаких `prune` и `pull`, только объекты `lidogram-*`, общие настройки не
    трогаем, чужое не чиним;
  - стоп-условия;
  - три паузы на подтверждение пользователя: перед первой записью на сервер, перед изменением
    nginx и после сравнения снимков.
- Найдено в коде и на сервере:
  - образ `postgres:17-alpine` общий с другим проектом, поэтому `pull` незаметно поменял бы
    чужую базу;
  - строка `listen [::]:443` сделала бы наш сайт сайтом по умолчанию для всех доменов по IPv6;
  - распаковка архива поверх папки оставила бы удалённые файлы при повторном деплое;
  - бэкап через `sh` мог молча записать пустой дамп;
  - Next сам делает редирект относительным, так что правка nginx не нужна (проверено по коду
    Next).
- Наша доля ресурсов хоста ограничена: память и CPU на каждом сервисе, `cap_drop` и
  `no-new-privileges` на Node-сервисах.
- Из плана убраны имена соседних проектов, домены и расписания: файл уйдёт работодателю.
